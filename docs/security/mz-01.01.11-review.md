# MZ-01.01.11: an independent review of the new code, and the scan

This release adds two-step sign-in, single sign-on, the backup key, a `stable` channel and browser tests. Its code was read by a second reader who was given the code, not the conclusions, and scanned with Checkmarx One.

## The independent review

The reader was asked for defects that can be exploited or lose data in: two-step sign-in (`src/mfa.js`, `src/iam.js`, the sign-in routes), single sign-on (`src/oidc.js` and its routes), the backup key (`src/backup-key.js`, `src/backup.js`, the scripts and routes), the workflows, and the activation codes. No critical or high finding; four medium and two low, two of them confirmed by running a server against the tests' mock identity provider. All six are fixed in the release.

| Severity | Where | What was wrong | What changed |
| --- | --- | --- | --- |
| Medium, confirmed | `src/server.js` (`ssoState`, `passwordNotEnough`) | "Only Admins may still sign in with a password" and the single sign-on button both depended on the server having an https address, which anyone with the links permission (a Security Analyst) could change: the button went, people who only use single sign-on were locked out, and a non-Admin's password worked again. | The password rule depends only on its own switch. While single sign-on is on, the server's address is changed only by an Admin and must stay an https address; an http value under Settings no longer hides a good `REPORT_SERVER_URL`. |
| Medium, confirmed | `src/server.js` (`POST /api/me/password`) | Someone signed in by single sign-on, who has no password here, could set one without knowing any, and so keep a way in after being removed at the identity provider. | A session made by single sign-on cannot set a first password: an Admin gives one under People & roles. |
| Medium | `src/server.js`, `src/oidc.js` | Single sign-on found the person by email address alone, Admins included, and the check that the provider verified the address can be turned off. | At a person's first single sign-on the provider's issuer and its own id for them (`sub`) are kept with the person, and required from then on. An Admin can reset that link. An address the provider did not mark verified is never accepted for someone whose role manages people, unless they are already linked. |
| Medium, needs write access to the repository | `.github/workflows/promote-stable.yml` | An image built from a version tag could be promoted to `stable`, and a tag can be pushed on a commit that was never merged, whose own copy of the workflow would build and sign it. | Only an image built from main can be promoted. |
| Low | `src/server.js` | With "add them with this role", a removed person was added again at their next single sign-on, and with no email domains listed anyone the provider signs in got the role. | Adding people needs at least one email domain; the page and the docs say that a removed person comes back unless disabled instead. |
| Low | `src/oidc.js` (`start`) | The cookie that ties a single sign-on round trip to one browser was reused when the browser already presented one, so one planted by someone else was kept. | A new cookie value at every start. |

### Checked and found sound

- **The ID token**: only RS256, PS256 and ES256; `none` and HS* refused; keys named in the token itself ignored; RSA keys of at least 2048 bits; issuer, audience, expiry, issue time and nonce all checked.
- **The round trip**: state is random, used once, lasts ten minutes and is tied to the browser; PKCE; the redirect address comes from settings, never from the request.
- **Outgoing calls**: https only, link-local and cloud metadata addresses refused, redirects not followed, limits on time and size; only an Admin sets the provider's address.
- **Two-step sign-in**: no session before the code; five wrong tries per sign-in, which also count towards the account's lock; a code works once; recovery codes are kept as hashes and work once; a reset leaves nothing in the last good copy; a lower role cannot reset an Admin's.
- **Nothing secret leaves**: no two-step key, recovery code, client secret or token in any answer, the audit log, the activity log or a diagnostics download.
- **The backup key**: 160 random bits, used through scrypt and AES-256-GCM, kept with mode 0600 and no last good copy, in no backup, email or log; shown only with the backup permission, and each showing is audited; a wrong key fails before anything is written; a folder that holds any earlier state is never judged a new installation.
- **The workflows**: the promotion's input reaches the script only as a checked value; it holds only the right to write packages; the browser tests run with a read-only token and no secret.

### By design

- Signing in with a Checkmarx One API key is not asked for a two-step code and is not covered by "Only Admins may still sign in with a password": it is the identity provider's (Checkmarx One's) sign-in, for people mapped to that identity.
- A session made by single sign-on ends when it idles out, not at the moment the person is removed at the provider. Disable the person here to end it at once.

## The Checkmarx One scan

Scan f0c053ad of the release branch (61a8fb0), with SAST, SCA, KICS, containers, secret detection and API security (the AI engines cannot be asked for through the connector), found 33 results, 3 of them new:

| Severity | Where | Result | Verdict |
| --- | --- | --- | --- |
| High | `test/oidc.test.js:127` | Secret detection: an address with a user name and a password | A made-up address in a test, which checks that the identity provider's address refuses one. Not a secret. It is now put together in code (a197abb), as the other tests do. |
| Medium | `src/mfa.js:74` | Client_Weak_Cryptographic_Hash | The two-step code is HMAC-SHA1, as RFC 6238 defines it and as every authenticator app computes it; another hash would make codes no app could produce. The known weakness of SHA-1 is finding two inputs with the same hash, which does not help against an HMAC with a secret key. Not exploitable. |
| Low | `src/oidc.js:71` | Secret_Leak_in_Error_Messages | The flagged value is `keys`, a true-or-false mark on an error saying whether the provider's signing keys should be read again. No key, token or secret is in the error or its message (the review above checked the messages). Not exploitable. |

Scan e20ac30a of the final code (a197abb) found 32 results: 1 critical, 4 high, 10 medium, 16 low and 1 info. The test's address is gone; the two results above are the only ones in this release's code; the others are in code this release does not change and were judged in earlier reviews ([MZ-01.01.10](mz-01.01.10-review.md)).

Marking the results judged not exploitable in Checkmarx One is a separate step, done with the maintainer's confirmation; the release does not wait for it.

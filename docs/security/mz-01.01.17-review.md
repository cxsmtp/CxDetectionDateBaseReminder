# MZ-01.01.17: the first scan that reported on the server's and the page's main code

## What the scan showed, and what earlier scans had not

Checkmarx One scan `fb266f9f` of this release's code (commit fa19de9; SAST, SCA, IaC, containers, secret detection, API security) lists **217 results: 1 critical, 6 high, 85 medium, 122 low, 3 info**. 190 of them are reported for the first time. The scan before it, `d79bed45` of MZ-01.01.12's code, listed 32.

The difference is not new code. Until MZ-01.01.13, most of the server was one file of 12,000 lines (`src/server.js`, 669 KB) and most of the page another of 13,700 (`public/app.js`, 727 KB). **No scan of this project ever listed a result in either file, in any state.** MZ-01.01.13 split them into `src/routes/` and `public/app/`, and this is the first scan since: 142 of the 190 are in the files the split made, 12 in what is left of `src/server.js`, 34 in other server files whose flows end in route code, and 2 in other page files. Each flagged line that was opened existed unchanged before the split.

So the "32 open, each judged before" that MZ-01.01.10 to MZ-01.01.16 reported was true of what the scans listed and said nothing about the two largest files. Why the engine was silent on them is not known (the connector shows no engine log; both scans counted about the same lines of code). The status pages of those releases are left as written, and this page is the correction.

Nothing in Checkmarx One is marked: every one of the 217 is still **To verify** there. The judgements below are this review's, to be recorded in Checkmarx One by someone with the right to change a SAST result's state.

Also not explained: six results of the earlier scan (four high `Reflected_XSS` in `src/govern/routes.js`, one in `src/govern/notify.js`, one in `src/fusion-git.js`) are absent from this scan although those files did not change. They were judged not exploitable in [MZ-01.01.11's review](mz-01.01.11-review.md).

## How the 190 were reviewed

Three readers, none given a conclusion to confirm: the six high results by the release's author, 140 information-type results by a second reader, 44 flow-type results by a third. Each was asked to judge from the code, and to say what was read against what was inferred. The data flow was fetched from Checkmarx One for 16 of the 190 and the rest judged from the flagged line and its callers; where one line carries several results they were judged together.

| Kind | Results | Real, fixed here | Not exploitable, hardened here | Not exploitable |
| --- | ---: | ---: | ---: | ---: |
| High (stored and DOM XSS, prototype pollution, reflected XSS) | 6 | 0 | 3 | 3 |
| Information exposure, PCI, privacy and secret-leak queries | 140 | 0 | 1 | 139 |
| Log forging, loop conditions, redirects, framing, plain HTTP | 44 | 4 | 1 | 39 |
| **Total** | **190** | **4** | **5** | **181** |

One of the 139 is not a false alarm but a decision: the first Admin's password in the server log, under "Left as it is" below.

No result lets someone who is not signed in, or an ordinary User, read or change anything they should not. The four real ones need a Security Analyst's or an Admin's permissions, or another calculator user's click.

## Fixed in this release

| Severity | Where | What was wrong | What changed |
| --- | --- | --- | --- |
| Medium: one signed-in person with the email-template permission (Admin, Security Analyst) could stall the server | `src/template.js` (`renderWithStack`), reached from `POST /api/settings/template/preview` | The renderer limited nesting, repeats and output, but not the text it reads: a section's body is read again for every repeat of every level around it. A 3.9 MB template of three nested sections over the preview's 12 findings took about 25 seconds of the server's one thread (measured with the renderer alone), and a saved one cost the same at every reminder. | The text read is counted, 64 MB at most for one render; beyond it the template is refused with a message. | Low: Admin only | `src/backup.js` (`describeBackup`), `src/server.js` (the line after a staged restore) | A backup's own time and host name are outside what its checksum covers and were printed as they came: a restored file could write a line of its own into the server log. | The time is shown only when it is a time as a backup writes it, the host name without control characters, and the log line passes both through the log's cleaner. |
| Low: one calculator user against another, in the browser only | `public/calculator/model.js` (`aheadMonths`) | A saved projection report kept any number of months, and downloading it looped that many times: a colleague's tab could be frozen. | At most the 60 months a projection covers. |

## Hardened, though not exploitable as found

- **Counts in a report's verification section** (`public/app/reports.js`, two high `Client_DOM_Stored_XSS`): rounds, baselines and fixed counts are numbers the server computes, and were put into the page as they came. They now go through the number formatter, so nothing stored can reach the page as markup.
- **The settings save's section names** (`src/routes/settings.js`, high `Prototype_Pollution`): a key such as `__proto__` found something on the list of sections and was then refused by the permission check. It is now refused because it is not a section at all. A test posts both names.
- **Words from the server or Checkmarx One to someone not signed in** (`src/routes/hands-off.js`, `src/routes/reports.js`, `src/server.js`): an emailed one-click link and a reply by email answered any error with its own message, and a project report's read passed on Checkmarx One's. Only a refusal raised on purpose is shown now; anything else is "something went wrong" to the reader and the detail in the server log. Three of these four places were found while reading, not listed by the scan.
- **One log line** (`src/routes/people.js`): an email address and a mail server's error are cleaned before they are written.
- **The calculator's Fusion read** (`src/routes/calculator.js`, found while reading): one read of a tenant at a time, as the main read already was.

## Judged not exploitable, with the reason

- **`Client_DOM_XSS`, twice (high), `public/app/core.js`**: when the server answers that it now takes HTTPS only, the page goes to the address in that answer, which must begin `https://`, with the path and query it already had. The address is the server's own answer; no script scheme can be given.
- **`Reflected_XSS` (high), `src/routes/tracked-reports.js`**: the "input" is the signed-in session. The route (needs the permission to view reports) builds a report from stored data with the report builder's escaping and sends it as a file to download.
- **Error messages (65)**: Checkmarx One's and the identity service's errors pass through a scrubber that removes tokens and keys, mail errors and git errors through their own; the report routes already answer with the kind of failure only. Eight are a callback parameter named `e`, not an error. Eighteen are connection and certificate tools only an Admin can call.
- **"PCI" (33) and "privacy" (26)**: "credit" and "balance" are Checkmarx One AI credits. The personal data that is logged is an email address, to the server's own log, which no route serves.
- **Secret leak (14 of 15)**: the word "password" as a way of signing in, a true-or-false, a time, a certificate's description. The one real secret is below.
- **Log forging (14)**: every one ends at the log's cleaner; the audit and activity logs are one JSON object a line, so no line can be forged there.
- **Loop conditions (8)**: a cache's eviction loop that runs at most once for each insert, a one-item list behind a signature check, or a capped value.
- **Redirects (13)**: to the server's own HTTPS address or an http(s) address an Admin set. Three are text replacements the query took for a change of address.
- **Framing and plain HTTP**: every answer carries `X-Frame-Options: DENY` and `frame-ancestors 'none'`; the HTTP listener only redirects once HTTPS-only is on.

## Left as it is, on purpose

- **The first Admin's generated password is printed to the server log** (`src/routes/session.js`, `Secret_Leak_in_Logs`). It is how a new installation's first Admin gets in when no password was given: used once, changed at first sign-in, and documented. Whoever can read the container's log before that first sign-in can use it. Printing the path of a file only the server's user can read would close that; it changes the installation steps and three pages of the docs, so it is the owner's decision.

## What this review did not establish

- The flow from source to sink was fetched for 16 results; the other 174 were judged from the code at the flagged line. For 11 flow results and one line of the mail reader the sink was inferred.
- Why earlier scans listed nothing in the two large files. The largest code file today is `public/calculator/page.js` at 216 KB, and the scan lists a result in it, so no code file is now larger than one the engine is known to read; whether a file between that size and the old 669 KB would be read is not known.
- What a mail server, a git host or Checkmarx One puts in its error answers at a given installation, beyond what the scrubbers remove.
- Whether the container's log leaves the host, and who besides Admins holds the audit permissions.
- Memory use of a calculator read of 50,000 projects, and whether the findings cache can be filled to exhaust memory.
- A git host's error answer (`ScmError.body`) is sent to a signed-in person uncut. Nothing is known to leak through it.
- The 25 seconds for the template is one measurement of the renderer alone, not of a running server.
- This release's own changes after the scanned commit (Safari's form controls, and the fixes above) have not been scanned.

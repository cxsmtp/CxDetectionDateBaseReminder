                Replace the whole image (a new Node.js or OS base) Beta Companion not running
                
              Updates above replace CxMissionZero's own files. Rarely, a release needs a new base image, and the page says so. The update companion, a second small container, can then replace the whole image from here. It downloads the image while this server keeps running, stops this server (which saves first, as for any update), and starts the same container on the new image with the same settings. If the new one does not start, it goes back to the old one.
              
                
              
                  
              
                    
                    
                  
              
                  
              
                
              
                
              
                  
              Start the companion once, on the server (Windows cmd, one line):
              
                  
              podman run -d --name mission-zero-updater --user root --restart=always --security-opt label=disable -v mission-zero-data:/data -v /run/podman/podman.sock:/run/podman/podman.sock ghcr.io/cxsmtp/cxdetectiondatebasereminder:latest node src/companion/main.js
              
                  
                  
              It needs the Podman socket, which can manage every container on the machine, so it does one thing only: it replaces the container named mission-zero, and only with this app's own image (UPDATE_IMAGE), at the version chosen here. It opens no port. Use your own volume name if it is not mission-zero-data; on a rootless Podman machine the socket is /run/user/1000/podman/podman.sock. Without the companion: podman pull ghcr.io/cxsmtp/cxdetectiondatebasereminder:latest, then your usual podman run --replace … line.

                GitLab, Azure DevOps and Bitbucket
                
              
                Each token is stored on this server like the SMTP password, never shown again, and only ever sent to its own host. Read-only scopes are enough. Or set them in the .env file (GITLAB_TOKEN, AZURE_DEVOPS_TOKEN, BITBUCKET_TOKEN…).
                

              
                
                GitLab 
                
                A personal, group or project access token with read_api and read_repository. Blame through the API, GraphQL user batches, profiles, and commits by name.
                
                
                
                  
                  
                  
                  
                
                
                
                
                  
                  
                  
                  
                
                
              
                

              
                
                Azure DevOps 
                
                A personal access token with Code (read), Graph (read) and Identity (read). Azure DevOps has no blame API: blame uses git on a clone made with this token. Usernames: the organisation directory, identity search, commits.
                
                
                
                  
                  
                  
                
                
                
                
                  
                  
                  
                  
                
                
              
                

              
                
                Bitbucket 
                
                Cloud: an app password (with your username) or a workspace/repository access token, read access to repositories and the workspace. Bitbucket Cloud has no blame API, and never shows users' email: blame uses git, and usernames are matched through commit authors. Data Center: an HTTP access token; blame through its API, and its user directory.

                    What the credits give back

The hours, at what a developer's hour costs, set against what the credits cost, are the return. The figures follow the Triage & remediation tab.
